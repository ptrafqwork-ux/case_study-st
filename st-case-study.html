The Problem

Four navigation systems.
Zero clear paths.

01

Grouped by org chart, not user need

Related information split across sections. The same need led to different places depending on which menu you tried.

02

Deep hover menus, walls of text

Four nav systems, 30+ items across nested layers. Key information buried several layers down. Technically reachable. Practically invisible.

03

Links that looked like body text

No colour, no underline, no shape. Staff had been manually pointing users to the right pages.

04

Duplicate entry points everywhere

Twelve topics in two or three menus. Worst offender: Contractors appeared in three separate navigation systems.

The problem wasn't missing content. It was missing structure. The path from user intent to content didn't exist.

Understanding the system

Mapped everything before
touching anything.

Audited every section, L2 page, tab, and nav element into Google Sheets — what exists, where it lives, what stays, what goes, what's missing. Became the content liaison across ST departments: confirming ownership, accuracy, and gaps.

What surfaced: duplicates, orphaned pages, related content separated across sections, and an entire site organised by which team created the content rather than who needed it.

The decisions

Rebuilding micro IA under
a moving target.

The mid-project reset

Initial direction: user-oriented topics. February: leadership changed the high-level IA to a corporate communications structure. The high-level was their call. I rebuilt the micro IA underneath — repositioning content, regrouping pages, redefining relationships under a new taxonomy. No timeline extension. Launch date didn't move.

The old navigation was optimised for reach — every destination accessible in two hovers. But reach isn't findability.

Old: optimised for speed

Hover menus exposed 30+ items simultaneously. Zero clicks to reach any destination. But one wrong mouse movement collapsed the menu. Users could reach anything in 2 hovers. In practice, they called staff.

New: optimised for confidence

Progressive disclosure — 3 to 6 choices per step, each legible, each leading somewhere predictable. More clicks, but each click is confident. Users see where they're going before they commit.

New stepped path

Stakeholders → Electricity → Licensing → Application list → Detail + CTA

Negotiating with content owners

Client wanted the static HTML table made interactive — hyperlink rows to PDFs, remove the cards. I pushed back: every PDF download across the portal uses the card pattern. One section breaking that means users re-learn how downloads work. Table stays as reference. Cards handle downloads.

Some feedback was accepted. Some was challenged. Some was negotiated into a middle ground. Every decision had a reason I could articulate to stakeholders who had their own valid priorities.

Interface design

UI that reinforced
the architecture.

Horizontal cards for scannable options. Stronger link and CTA treatment — the old site had links that looked like body text. Topic landing pages showing only subtopics. Inside pages with one job: get the user to the next step.

Homepage styling was handled by my creative director. Inside pages were mine.

Implementation

Surviving
Drupal.

New IA meant new taxonomy in the CMS. Content retagged, reassigned, realigned — on a live system still serving users. I was in the CMS doing it: editing, uploading, checking layouts, overseeing migration across dozens of pages.

If I'd handed off the IA as a document and walked away, the structure would've degraded the moment operators started working without the new logic enforced. Staying was deliberate.

Drupal backend — taxonomy and content editing

What the reset exposed

One upstream change cascaded into rework at every layer.

IA → Taxonomy → Content → Design → Implementation

The February IA change landed after micro IA was being built, content was being mapped, and design had started. No timeline extension. This exposed the dependency chain I now carry forward: map dependencies early, lock IA–taxonomy relationships before implementation starts, identify content ownership before content needs to move.

Reflection

What I
took away.

What I'd do differently

Map dependencies earlier. Lock taxonomy before implementation runs. Identify content ownership before migration starts. Build validation checkpoints so upstream changes get caught before they cascade.

What this made me better at

Holding the thread across IA, taxonomy, content, design, and implementation simultaneously. These layers are tightly coupled. On this project, I was that thread.
